## Issues & Friction

- First repair attempt (180 withheld frames against the shared single-cell
  wall) failed at frame 97 with eye x = 1.78297 > 1.78: the character was
  riding up the 0.25 m cell via autostep, not blocked. lengthening the press
  (the whole point of withholding) made it worse — full mount by frame ~116.
- Test-runner stdout (including `eprintln!` probe traces) is swallowed by the
  harness; probe values were recovered through panic messages, which do
  surface. Minor workflow friction, no product impact.

## Decisions & Rationale

- No production changes: the fault was test-side (fixture + timing
  assumptions). The publication contract (`detail_cadence.rs` docs) already
  guarantees exactly what the repaired test asserts: queueing never touches
  live collision; only `step` publishes; removals never gate.
- Tall column over bound relaxation: raising `BLOCK_LIMIT_X` past the 1.783
  ride-up would have blessed climbing over a solid wall as "blocked". An
  impassable fixture tests the stated property honestly.
- Coalesced single `on_edit` for the two-cell removal burst: keeps one source
  version in flight so the buffered-completion wait is exact; per-edit
  supersession is covered by `repeated_and_reversed_edits_publish_only_the_final_source`.
- `saw_pending || saw_buffered` instead of requiring pending: requiring
  pending would reintroduce a worker-slowness assumption; the disjunction is
  deterministic (first sample after `on_edit → Ok(true)` always shows a
  tracked state) while still proving a real scheduler state was covered.

## Solutions Applied

- `crates/matterweave-physics/tests/detail_cadence.rs` only: local tall-wall
  fixture, four-phase withheld/publication/walk-out structure, crossing-band
  eye-height check, `queued + inflight + results` tracking (buffered counts
  as pending since only `step` may publish it).
- Former short-pending-window masking documented in a test comment: the old
  test walked only until publication (tens of frames), never reaching the
  ~95-frame autostep mount, so the climbable single cell looked blocking.

## Insights

- Fixture geometry must be validated against the character controller
  (autostep 0.30 m over quarter-metre stairs), not just against the collider
  layout: a "wall" shorter than the step limit is a staircase.
- Withholding `step` is the only timing-assumption-free way to test
  pre-publication behavior; any assertion of the form "observe N pending
  frames" is a race against the worker by construction.

## Publication-contract audit (brief, no implementation change)

- Contract reviewed in `src/detail_cadence.rs` docs + `AsyncDetailCollision`
  queue code: single pending/running/buffered slot, latest-wins, version +
  epoch tagging, gate retention, staged sync fallback. Test usage matches the
  documented caller convention (one `step` per frame before physics stepping,
  `on_edit` per edit burst, `reset` on replacement).
- Substantive remaining risks:
  1. `on_edit → Ok(true)` assumes a live worker; thread-spawn failure flips
     the test to the sync path (`Ok(false)`) and it fails loudly — correct
     but environment-sensitive (no issue on target devices with threads).
  2. Rest-penetration bound (1.78 vs 1.683 observed, 97 mm margin) is
     empirical; a Rapier version bump changing contact slack could erode it.
     The mutation probe and the walk-out band check provide defense in depth.
  3. Mount-vs-block behavior lives in the character controller, not the
     cadence: any future fixture shorter than the autostep limit reintroduces
     the masked-climb hazard. The test comment records the rule (fixture rise
     must exceed 0.30 m).
