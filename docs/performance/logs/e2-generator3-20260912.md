# Engineering log w_4ebeb178

Worker: `opus-medium` · outcome: Category: implement · run: `/mnt/bench/matterweave-dev/completion-20260912/collector-generator3-opus`

Scope: make `tools/performance/collect_wetland_pair.py` compatible with the app's
current showcase generator without weakening any safety gate. Base commit `da2e4fc`.

- **Actions Taken:**
  - Read the real app recovery semantics before editing:
    `apps/explorer/src/wetland_state.rs` (`SavedWetland::validate`,
    `load_recovering_with`: an invalid base is what makes recovery slots be
    scanned, and every candidate is validated against the caller's generator),
    `apps/explorer/src/wetland.rs` (`GENERATOR = matterweave_detail::SHOWCASE_GENERATOR_VERSION`,
    `SEED = SHOWCASE_SEED = 20260908`, the `WETLAND LOADED: {cells} cells / {instances} placed objects`
    line built from `scene.counts()`), and
    `crates/matterweave-detail/src/showcase.rs` (`SHOWCASE_GENERATOR_VERSION = 3`).
  - Replaced the hardcoded `EXPECTED_GENERATOR = 2` with a manifest-derived
    generator: new `resolve_generator()` requires every frozen `*-build.json`
    to declare the same supported generator (`SUPPORTED_GENERATORS = (2, 3)`,
    `CURRENT_GENERATOR = 3`) and threaded that value through `check_fixture`,
    `preflight_files` (base-save invalidity), `finish_and_pull` (recovered
    session revalidation), `run_trial`, and the run `manifest.json`.
  - Replaced the single `EXPECTED_COMPOSITION`/`EXPECTED_SCENE` pair with
    `KNOWN_COMPOSITIONS`, mapping each frozen composition hash to its generator
    and its exact full-world counts;
    `resolve_expected_scene(apks, generator)` now also rejects a composition
    whose generator disagrees with the manifests.
  - Reordered `main()` so build manifests are read and the generator resolved
    *before* the fixture is validated, and all of it before `Device` exists.
  - Tests: kept every historical gate (generator-2 byte literals still validated
    against generator 2) and added generator-3 and mismatch coverage, plus a
    `main()`-level `StartupRejectionTest` that patches `Device` to raise if it is
    constructed at all.
  - Documented the contract in `docs/performance/measurement-qualification.md`.

- **Issues & Friction:**
  - The counts the collector must expect are not in the collector's own history
    for generator 3. They were taken from
    `docs/evidence/full-wetland-generator3.json`
    (`counts.instance_expanded_occupied_cells` 34716467, `counts.instances` 8302,
    composition `dfb9f40519a3c151`, seed 20260908), which
    `crates/matterweave-detail/examples/showcase_manifest.rs` writes from the same
    `Showcase::counts()` fields the app formats into `WETLAND LOADED`. No number
    was invented or recomputed by hand.
  - `check_fixture` gained a required positional argument. `check_phone_route.py`
    (owned by another worker) imports only `Device`, `Ownership`,
    `base_save_is_invalid_for`, `enter_wetland`, `final_cleanup`,
    `install_and_verify`, `record_environment`, `sha256_file` — none changed
    signature — so it is untouched and still passes its tests.

- **Decisions & Rationale:**
  - Manifest-derived rather than a new constant or a CLI flag: the generator is
    already a required, hash-verified field of the frozen build manifest, so it
    cannot silently disagree with the APK under test, and a mixed pair is
    rejected instead of being reconciled.
  - Generator 2 retained, not deleted: the existing frozen generator-2 paired
    experiment must stay reproducible. It is accepted only when *both* manifests
    declare it, together with its own composition and counts.
  - Gates were tightened, not relaxed: unsupported/mixed/non-integer generators,
    a composition/generator disagreement, and a boolean `generator` in the
    fixture are all new rejections. Full-world count checking stays exact.

- **Solutions Applied:**
  - `resolve_generator()` + `KNOWN_COMPOSITIONS` + threading one validated
    generator through every generator-dependent gate; fixture/manifest
    agreement is now decided before any `adb` call.

- **Insights:**
  - The base-save invalidity gate is generator-relative in both directions: with
    generator 3 under test, a user's *current* session now correctly blocks the
    run (their save must never be overwritten), while a stale generator-2
    session correctly does not. Hardcoding generator 2 inverted both cases.
  - `SavedWetland::load_recovering_with` validates every recovery candidate with
    the same generator, so a fixture written for another generator would have
    been skipped on the device and the trial would have measured a fresh
    session; rejecting it on the host is the only fail-closed option.
