# v0.3 delivery and coordination plan

Recorded: 2026-09-07. Basis: the owner's v0.3 planning and multi-model coordination
discussion. This is the intended delivery protocol, not evidence of implemented
v0.3 features. [STATUS](STATUS.md) remains the record of actual accomplishments.

## Outcome and sequence

Deliver an ash/direct Vulkan Android release with dynamic sunlight shadows,
smoother bounded streaming and a repeatable destruction playground. Advance M2/M3
and the direct-light foundation of M4; full GI, reflections and automatic LOD remain
later gates in the [roadmap](ROADMAP.md).

1. Inspect current implementation and qualifying existing solutions. Capture a
   repeatable v0.2 device baseline. Separate generation, meshing, collision,
   uploads and saving costs before deciding which work to move or budget.
2. Settle shared sun/settings, immutable job-input/result, collision-publication
   and scenario/persistence interfaces before dependent writers start.
3. Implement directional shadow depth rendering, filtered sampling and stable
   movement, including terrain, dynamic bodies and off-screen shadow contributors.
   Keep a shadows-off comparison. Add cascades only if coverage/quality warrants.
4. Prepare terrain/meshes through bounded jobs. Validate chunk revisions and
   residency generations at publication; reject obsolete results. Bound queues,
   result memory and uploads. Collision must be ready before newly available
   terrain becomes traversable, and delayed work must not undo edits.
5. Build a breakable structure and repeatable reset/save scenarios using existing
   voxel bodies. Preserve explicit body limits; measure before expanding them.
6. Integrate incrementally and run focused renderer comparisons on stable
   fixtures, recording adopt/revise/defer conclusions in the affected ADRs.

The lead coordinates shared interfaces, app integration, lockfiles, builds, phone
access, review and delivery. Workers perform most bounded implementation and
investigation. Do not multiply writers before independent work is ready.

## Durable state and one authority

Use one local SQLite board for a run, shared by all its worktrees. The existing
skill's `scripts/coord.py` was evaluated as a storage candidate. The independent
[project access layer](../tools/coordination/README.md) now implements the bounded
protocol with 16 rehearsal tests; the execution log records actual startup and
worker registration. Preserve its documented manual-supervision limits when
launching/replacing workers. Do not infer filesystem fencing from a board update.

Choose the canonical run directory under the Git common directory, obtained with
`git rev-parse --path-format=absolute --git-common-dir`, for example
`matterweave-runs/<unique-run-id>/`. This is untracked durable local state, not a
temporary worktree or `/tmp`. Record the selected path in every launch contract.
Formal benchmark data belongs under `/mnt/bench`; publish durable release evidence
and commit compact reports according to [BENCHMARKS](BENCHMARKS.md).

The board's current snapshot is the sole live assignment and accepted-interface
authority. The lead alone updates it using expected-version checks. An input file
uploaded into the board is not a second live ledger. Workers replace their own
status documents and submit handoffs/proposals. Native messages are notifications
or urgent steering with board decision/message pointers, not competing contracts.

At phase changes, record accepted engineering decisions, evidence and next actions
in repository documentation. Local runtime IDs and mailboxes need not be committed.
A fresh clone can resume from the repository; on the original machine a recovering
lead also reconciles live processes and worktrees before assigning writes.

## Ownership and task lifecycle

Every assignment records task ID, attempt ID, unique worker instance, route/effort,
base revision, exact worktree and owned paths/resources, dependencies, interface
versions, acceptance checks, runtime/process identifiers and evidence locations.

- Use one writer per isolated worktree. The lead allocates shared paths and
  external resources; worktrees still share Git refs, caches and host services.
- Use `ready -> running -> submitted -> accepted`, plus `blocked` and `revoked`.
  Worker completion is submission; only the lead accepts a checked revision.
- Workers verify their active attempt and relevant interfaces before editing
  phases and submission. Discovered overlap becomes a blocker/proposal.
- Before reassignment, stop the exact previous worker and its child processes,
  verify quiescence and inspect/preserve changes, then increment the attempt.
  A timeout or board update never revokes filesystem access. Late submissions
  from old attempts cannot override current ownership or acceptance evidence.
- Review a stable revision. Later changes invalidate affected review evidence.
  Schedule expensive builds and exclusive phone operations through the lead.

SQLite transactions protect board updates, not source files. The helper's actor
name is self-declared, not authentication. Keep the board within the trusted run
and use verified harness permissions where available. Maintain one active lead
and a supervisor-held exclusive local lock when implemented; takeover must verify
that the previous lead and its writers are inactive. Do not treat an expired
heartbeat, PID file or helper flag as proof of exclusive leadership.

## Bounded reads and message protocol

The wrapper must enforce the following working limits, rather than relying on
each model to remember them. Keep required contract facts intact; split oversized
assignments or retrieve specific referenced sections instead of silently truncating.

| Item | Working limit/policy |
| --- | --- |
| Worker startup | Aim for 1,500 tokens of contract and applicable current decisions; enforce a 6 KiB UTF-8 body cap, which is not an exact token cap. |
| Ordinary message | At most 1 KiB, one actionable change/question and evidence pointer. |
| Inbox batch | At most four messages and 8 KiB serialized output; paginate without losing pending messages. |
| Global current snapshot | Existing 8 KiB hard body limit; active work only. |
| Worker current status | At most 2 KiB; replace progress rather than append a diary. |
| History/logs/diffs | Retrieve by explicit ID/path/revision and bounded range; never dump full history. |

Workers receive their assignment and applicable current decisions, not the whole
global snapshot on every interaction. The lead reads changed versions and targeted
status records. The raw helper's inbox can return 100 messages of up to 4 KiB each,
and `state` lists all historical worker documents: neither unrestricted interface
belongs in routine supervision. Archive completed task detail outside the current
snapshot; avoid making an ever-growing archive index part of startup context.

Use targeted `decision`, `blocker`, `question`, `update`, `handoff` and `control`
messages with run/task/attempt identity, decision version when relevant, required
action and evidence reference. Coalesce ordinary progress in status documents.
Do not broadcast logs or exchange acknowledgment chatter. Check inboxes at phase
boundaries, after long tool calls, before dependent edits and before submission.
File messages do not wake models: urgent changes require verified steering or
stopping the owned process before conflicting work can continue.

Each inbox has one consumer. Process its ordered batch, durably record consequences
or deferred actions, then acknowledge only the returned processed boundary. The
raw helper permits skipping unread messages with a later acknowledgment, so the
wrapper must validate the delivered batch boundary. Receipt is not application:
an interface change needs explicit confirmation of decision version/task/attempt
before dependent work resumes. Unhandled urgent work must not be hidden by a
receipt cursor; retain it as pending until resolved or explicitly superseded.

Retry keys prevent duplicate sends. Record processed message/decision identifiers
with durable consequences and check actual side effects before replay; a crash
between an action and acknowledgment can redeliver a message. There is no general
exactly-once guarantee across SQLite, Git and processes. Superseding decisions name
their predecessors; never discard actionable old messages merely because they are
old. Reconcile them against current decisions and active attempts.

## Recovery and startup gate

Before dispatching v0.3 implementation writers, implement/reuse the bounded access
layer and rehearse these cases with local fixtures, without paid model calls:

1. Concurrent snapshot updates: one wins; the other rereads and reconciles.
2. Delayed old-attempt submission: rejected as current completion evidence.
3. Crash after action but before acknowledgment: replay does not repeat the effect.
4. Full inbox/oversized artifact: bounded output, continued pagination and no loss
   of pending actions; status churn does not create an inbox backlog.
5. Worker replacement: old writer/children are quiescent before new ownership.
6. Lead restart: reconcile run ID, leader, versions, pending actions, processes,
   worktree heads and submissions before allowing writes.
